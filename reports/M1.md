# AI Research Digest Agent

## Milestone 1: Planning

### 1. Task definition

The agent helps students and researchers keep up with recent AI papers relevant to their work. It builds an interest profile from user-provided material, such as an AlphaXiv or Google Scholar profile, recent project descriptions, and explicit interests or exclusions. Given this profile and a date range, it collects papers, removes duplicates and previously recommended items, and produces a digest of up to $N$ papers, where $N$ is configurable. Each entry includes a short summary, a source link, an explanation of relevance, and available evidence of community attention. Digests can be requested on demand or generated on a schedule.

The initial discovery source will be arXiv. Twitter/X will provide an additional attention signal through scrapers. Papers discussed by many distinct accounts may deserve inclusion, provided they match the user's interests. Attention will be reported separately from research quality.

The agent chooses its next action based on intermediate results. It can reformulate a narrow search, inspect the paper's main text when an abstract is insufficient, or investigate discussion around a promising paper. These decisions depend on retrieved evidence and the user's interests, which makes adaptive investigation useful beyond a fixed retrieval-and-summary script or a one-shot response.

The provisional model is GPT-5 mini. An alternative backend would use a model accessed through Claude Code or Codex CLI, with built-in tool execution disabled. The model generates queries, assesses relevance, selects evidence, summarizes papers, and requests actions through a structured interface. Application code validates and executes allowed requests. The backend choice will depend on pilot quality, budget, and whether the CLI supports this execution setup.

Code handles retrieval, date filtering, identifier normalization, deduplication, attention counts, storage, scheduling, and usage limits. A text encoder provides embedding similarities for preliminary relevance filtering, while the LLM assesses the remaining candidates in context.

### 2. Initial architecture

The agent uses one bounded ReAct-style loop: select an action, call a tool, inspect the result, and decide what to do next.

```text
User interests and date range
    -> Search papers and check recommendation history
    -> Filter by topic and keywords, then embedding similarity
    -> Assess remaining candidates with the LLM
    -> Read more and inspect X attention when useful
    -> Refine searches if needed
    -> Select papers and verify summary claims
    -> Produce and save the digest
```

Relevance filtering has three stages. L1 uses topic and keyword rules to remove obvious mismatches. L2 ranks candidates by cosine similarity between text embeddings of the interest profile and paper titles and abstracts. L3 uses the LLM to assess relevance against the user's specific goals and exclusions. Thresholds will be tuned on the pilot set to avoid discarding relevant papers before L3.

#### External tools

- `search_papers(query, date_from, date_to)`: retrieve arXiv candidates and metadata.
- `get_paper_details(paper_id)`: retrieve the abstract and source links.
- `read_paper(paper_id)`: retrieve the paper's main text when available, excluding references and appendices. Summaries must stay within the evidence retrieved.
- `search_paper_mentions(paper_id, title, date_range)`: scrape matching X posts, including available author identifiers, timestamps, and links.

#### Internal tools and memory

- `load_user_profile(user_id)`: retrieve interests and exclusions.
- `get_previous_items(user_id)`: retrieve previously recommended paper IDs.
- `save_digest(user_id, digest)`: save the digest and update recommendation history.
- `validate_digest(digest)`: check required fields, source references, and duplicate IDs.

During a run, temporary memory contains queries, candidate papers, retrieved evidence, and tool results. SQLite stores user preferences, canonical paper IDs, past digests, and recommendation history between runs.

#### Ranking and stopping

Relevance is the primary ranking criterion. X attention can boost relevant candidates and provide a separate "widely discussed" label. The initial attention measure is the number of distinct authors mentioning a paper within the same fixed window. Code excludes reposts without added commentary and repeated mentions by the same account. Matching uses paper links or identifiers first, with title matching as a fallback.

Scraped counts represent observed activity, not complete platform coverage. Failed collection is marked as unavailable rather than zero attention. Retrieved papers and posts are treated as source data, not instructions for the agent.

Each run has limits on search calls, full-text reads, scraper requests, and model usage. The agent stops when it has enough supported selections or exhausts its budget. It can return fewer than $N$ papers and disclose missing evidence or failed sources.

### 3. Failure map

The cases below are planning hypotheses identified from the proposed workflow. No prototype failures have been observed yet. The final column specifies how each risk will be investigated.

| Failure | Why it is plausible | Initial probe and response |
|---|---|---|
| Duplicate recommendations | Revisions and alternative links can refer to the same paper. | Supply two versions and a previously delivered paper. Normalize IDs and check persistent history. |
| Irrelevant selections | Keyword overlap can hide a different research problem. | Test an interest profile with an explicit exclusion. Require a relevance explanation grounded in the abstract or text. |
| Missed relevant papers | Narrow queries, early filtering, and arXiv-only discovery can omit relevant work. | Compare results with a manually prepared reference set, including terminology variants. Check losses at L1 and L2, adjust thresholds, refine queries, and state the source-coverage limit. |
| Unsupported summaries | The model may invent results or overlook evidence in excluded appendices. | Compare claims with retrieved passages and simulate missing main text. Record supporting evidence and state when an assessment uses only the abstract or main text. |
| Retrieval failure mistaken for no results | API errors or blocked scraper requests may produce empty outputs. | Simulate timeouts and access failures. Distinguish errors from valid empty results and use bounded retries. |
| Irrational tool use | The agent may repeat unproductive searches or follow instructions embedded in retrieved text. | Test an obscure topic and an injected instruction in source text. Inspect the action trace and enforce tool and budget boundaries in code. |

### 4. Initial evaluation plan

Prepare three research-interest profiles with exclusions and fixed date ranges. Build a frozen set of approximately 30 candidate papers, manually labeled as irrelevant, partially relevant, or relevant. Save source text and sampled X posts so repeated comparisons use the same inputs. Run one live integration check separately.

Compare the agent with a baseline using one fixed search followed by one summarization call. Also compare the agent's ranking with and without the X attention signal.

| Dimension | Evaluation |
|---|---|
| Relevance | Measure the proportion of selected papers labeled relevant and manually review relevance explanations. |
| Coverage | Measure how many relevant reference papers are retrieved and retained at L1, L2, and L3. This measures coverage of the reference set. |
| Summary accuracy | Check factual claims against abstracts or full-text passages and record the proportion supported. |
| Duplicates | Check repeated canonical paper IDs within a digest and across consecutive runs. |
| Attention usefulness | Verify sampled post-to-paper matches and ask readers whether attention-aware ranking improves which papers deserve mention without reducing relevance. |
| Reliability and rationality | Inspect traces for useful query changes, justified extra reads, correct handling of failures, resistance to source instructions, and timely stopping. |
| Efficiency | Record model usage, estimated cost, latency, and tool calls per digest. |

Provisional targets are at least 80% relevant selections, at least 95% supported factual claims, no duplicate recommendations, and compliance with every configured run budget. The pilot will test whether these targets are realistic.

The next step is a small prototype covering one topic, one digest, and selected failure probes. Its outputs will guide revisions to the architecture and failure map.
