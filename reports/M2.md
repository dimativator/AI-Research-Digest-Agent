# Milestone 2: Building and First Evaluation

## Reproduce

Run from the repository root. The project requires Python 3.12, Codex CLI, and an authenticated Codex account. No API key is added to the repository; `codex login` uses the CLI's local authentication.

```bash
conda env create -f environment.yml
conda activate ai-research-digest
python -m playwright install chromium
codex login
python -m eval.run_m2 --sample eval/sample.json --output eval/results.json
```

The evaluation makes live Codex calls. It uses the CLI default model unless `--model MODEL` is supplied. The frozen task input is local, but the model output is not deterministic, so repeat runs can differ. The detailed per-task predictions, errors, decisions, latency, steps, and calls are written to `eval/results.json`.

To re-create the sample from the saved SQLite run (replaces the current frozen sample):

```bash
python -m eval.freeze_sample --run-id c7b11e4a4d204ff38c017f34c318b59f
```

The sample includes the profile, date window, categories, full paper metadata, abstracts, and human relevance labels. `eval/freeze_sample.py` contains the documented manual annotations. The IDs and texts were captured from one completed run; future arXiv changes do not alter the committed sample.

## Evaluation Design

The frozen sample has 20 papers from one representative profile: LLM optimization, low-rank and memory-efficient training, spectral methods, PEFT, and the research-digest agent project. The date window is 2026-10-20 through 2026-10-24. The binary task is whether each paper is relevant to that profile. There are 9 relevant and 11 irrelevant labels.

Labels are a single annotator's manual judgments with short rationales. They are not the agent's screening labels. Boundary cases, including inference-time KV-cache efficiency and broad agent-memory work, are inherently debatable. There is no second annotator or inter-rater score, and this sample covers only one profile and one five-day arXiv slice.

We compare two methods on the same profile and frozen paper abstracts:

| Method | Why it fits | Level |
| --- | --- | --- |
| One-call baseline | Tests whether an LLM can make the same binary relevance judgment without tools or a loop. | Final task label only. |
| ReAct agent | Runs the production `DigestAgent`; it chooses whether to finish or inspect the paper, then the harness converts a non-empty digest to relevant. Frozen inspection returns unavailable rather than fetching changing pages. | Final task label plus recorded action path. |

The task-level label is the primary comparable outcome. We log the path to expose the loop's extra effort, but do not grade action quality in this first evaluation. The paper-level unit gives 20 paired judgments; repeated papers are not independent evidence about generalization.

## Results

Live run with Codex CLI 0.164.0 and its default model on 2026-10-25:

| Method | Accuracy | Precision | Recall | F1 | Mean LLM calls/task | Mean decision steps/task | Mean tool calls/task | Mean latency/task | Cost/task |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| One-call baseline | 75% (15/20) | 64.3% | 100% | 78.3% | 1.0 | 0 | 0 | 5.57 s | Unknown |
| ReAct agent | 80% (16/20) | 72.7% | 88.9% | 80.0% | 3.1 | 2.1 | 1.1 | 28.38 s | Unknown |

The loop improved accuracy by 5 percentage points and F1 by about 1.7 points in this sample. It was roughly 5.1x slower and used 3.1x as many LLM calls. The baseline had higher recall; the loop missed one manually relevant paper that the baseline accepted. This small sample does not establish a reliable quality improvement. CodexOpenAI does not expose token usage or price, so dollar cost is unknown, not zero. Latency is wall-clock time measured by the evaluation script and includes fresh Codex CLI process startup per request.

The agent's four classification errors were false positives on `2610.31069`, `2610.29424`, and `2610.30421`, plus a false negative on `2610.31633`. The baseline's five errors were false positives on `2610.28176`, `2610.31069`, `2610.31098`, `2610.29424`, and `2610.30421`. These IDs and per-task records are in `eval/results.json`.

There were no unhandled task errors in this evaluation. Tool calls count completed observations, not internal network requests. The agent's inspection fixture intentionally returns `unavailable`: this evaluation isolates decision-loop value on frozen abstracts, not full-text retrieval quality or live arXiv/X performance.

The CLI emitted non-fatal compatibility diagnostics that `tools.view_image` was ignored and Code Mode was unavailable; the adapter disables native tools, and all evaluation requests completed.

## Failure Analysis

Three retained cases follow. Only the first is from a live model run; the other two are explicit controlled reproductions from deterministic tests, not additional live failures.

1. **Live: final evidence quote rejected twice.** In trace events 77 and 80, the model chose `finish`; events 78 and 81 reject the decisions with `Final evidence was not shown to the decision model`. At least one inspection quote normalized LaTeX/punctuation (for example, `X k` rather than the retrieved math notation); several selected quote strings were not exact contiguous substrings. The harness then correctly required a retry, and the model eventually completed. Plausible root cause: the model paraphrased or normalized text despite instructions to copy exact quotes. See [live trace](../eval/failure_traces/01_live_evidence_rejection.json). A suitable M3 unit test freezes the prefix at event 78 or 81 and checks the next decision with tools stubbed.

2. **Controlled: unsupported tool and unscreened ID.** The model first requests `shell`, then tries to inspect `../../etc/passwd`. The protocol validator rejects both before any tool call; a valid decision subsequently completes the test. This is an expected defensive recovery, not an observed live model failure. See [invalid-action trace](../eval/failure_traces/02_invalid_tool_decisions.json) and [source test](../tests/test_digest_pipeline.py).

3. **Controlled: full-text inspection returns 404.** The model requests `inspect_paper`; the fixture returns `unavailable` with empty text. The agent retains the failure as an observation, completes using abstract evidence, and discloses the limitation instead of claiming full-text support. This is a source failure handled by the loop, not a live outage in the evaluation. See [inspection trace](../eval/failure_traces/03_inspection_unavailable.json) and [source test](../tests/test_digest_pipeline.py).

## M1 Plan Update

The M1 plan proposed three profiles, about 30 papers, separate L1/L2/L3 coverage, factual-summary review, duplicate checks, and an X-aware ranking comparison. For M2 we narrowed scope to one profile and 20 frozen abstracts so an end-to-end baseline comparison could be run and committed in time. We added an actual one-call baseline and measured per-task latency and decision/tool/model-call counts. We did not evaluate coverage stages, factual claim support, duplicate history, or X utility; those need dedicated labels/fixtures and remain M3 work. The M1 provisional 80% relevance target is neither passed nor failed conclusively by this small single-profile binary task result.

The prototype also differs from the initial M1 design: retrieval is arXiv plus BM25, screening, optional Arc/X, and Codex CLI behind a structured adapter. It does not use embeddings. The CLI harness and bounded persistent ReAct loop were retained because they provide auditable Python-owned tools and reproducible trace state without requiring a separate API key.
